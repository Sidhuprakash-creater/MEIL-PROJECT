## 2. FINAL ROLE DEFINITIONS — NON-NEGOTIABLE

The platform has the following organizational hierarchy:

GROUP
  └── SUBSIDIARY
      └── BUSINESS UNIT (BU)
          └── PROJECT / SITE
              └── Assigned Data Entry Users

The role hierarchy is:

1. Group Admin (also called Super Admin — the same role).
2. Subsidiary Admin.
3. Subsidiary Manager.
4. BU Manager.
5. BU Admin.
6. Seven Data Entry User roles.

The seven Data Entry User roles are:

- Environment Data User.
- Finance & Resource Contributor.
- HR User.
- EHS / Safety User.
- Procurement User.
- CSR / Community User.
- Compliance User.

### Subsidiary Admin — primary responsibility

The Subsidiary Admin is responsible for:

- Managing business units within the assigned subsidiary.
- Creating projects under the correct business units.
- Managing authorized organizational assignments.
- Setting reporting timelines at subsidiary, BU, and project levels.
- Using inherited deadlines by default.
- Monitoring submitted, pending, approved, rejected, and overdue reports.
- Opening and reading BU and project reports.
- Inspecting supporting evidence without leaving the report workflow.
- Monitoring user activity, reporting progress, missing submissions, and validation issues.
- Preparing subsidiary-level ESG reporting packages.
- Submitting eligible subsidiary reporting data to the Group Admin's reporting workflow.

### Subsidiary Admin must NOT

- Approve or reject BU reports.
- Approve or reject project reports.
- Override the Subsidiary Manager's review decisions.
- Create another Group Admin or grant Group Admin permissions.
- Access or modify another subsidiary without explicit authorization.
- Independently create or finalize the consolidated Group BRSR report.
- Override mandatory Group-level reporting policies without authorization.

The Subsidiary Admin's role is organizational administration, timeline management, reporting operations, and monitoring.

### Subsidiary Manager — separate role

The Subsidiary Manager is a separate role at the same subsidiary level.

The Subsidiary Manager is responsible for:

- Reviewing submitted BU and project reports.
- Inspecting the full report and its evidence.
- Approving or rejecting reports.
- Providing a mandatory rejection reason.
- Sending rejected reports back to the responsible BU/project user for correction and resubmission.
- Monitoring reporting progress and review queues.

The Subsidiary Manager cannot create new BUs or projects.

The Subsidiary Manager's approval decisions must appear in the Subsidiary Admin's report-monitoring views, but the Subsidiary Admin must not receive approval/rejection controls.

### Group Admin ownership

The Group Admin owns:

- Group-wide reporting governance.
- Consolidation across applicable subsidiaries.
- Final BRSR disclosure mapping.
- Creation and management of the consolidated Group BRSR report.
- Required Group-level sign-offs and finalization.
- Group-wide organizational and security policies.

The Subsidiary Admin may prepare and submit subsidiary-level reporting packages, but must never replace the Group Admin as owner of the consolidated Group BRSR report.

## 4. iOS LIQUID GLASS AND GLASSMORPHISM

Create a premium enterprise interpretation of iOS Liquid Glass.

Required treatments:

- Translucent white and pale-sky-blue surfaces.
- Controlled backdrop blur.
- Thin, cool-toned translucent borders.
- Subtle inner highlights.
- Soft ambient shadows.
- Layered depth and carefully restrained reflections.
- Gentle blue illumination around prominent panels.
- Smooth rounded corners.
- Clear separation between floating navigation and content surfaces.

Example starting CSS:

.glass-panel {
  background: rgba(255, 255, 255, 0.70);
  backdrop-filter: blur(24px) saturate(145%);
  -webkit-backdrop-filter: blur(24px) saturate(145%);
  border: 1px solid rgba(255, 255, 255, 0.84);
  border-radius: 22px;
  box-shadow:
    0 12px 32px rgba(50, 112, 158, 0.09),
    0 3px 8px rgba(50, 112, 158, 0.04),
    inset 0 1px 0 rgba(255, 255, 255, 0.88);
}

.glass-card {
  background: rgba(255, 255, 255, 0.78);
  border: 1px solid rgba(255, 255, 255, 0.88);
  border-radius: 20px;
  box-shadow: 0 8px 24px rgba(56, 113, 153, 0.07);
  transition:
    transform 220ms ease,
    box-shadow 220ms ease,
    border-color 220ms ease;
}

.primary-action {
  background: #20A779;
  color: #FFFFFF;
  border-radius: 12px;
  box-shadow: 0 5px 14px rgba(32, 167, 121, 0.20);
}

Apply these styles through reusable design tokens and components rather than duplicating CSS across pages.

Avoid excessive blur behind dense tables. Keep a solid or nearly solid surface wherever data readability is important.

Provide a fallback for browsers without backdrop-filter support.

Do not use neon colors, dark sci-fi dashboards, excessive gradients, oversized decorative elements, or emoji-based interface icons.

Use professional Lucide icons or the icon library already installed in the project.

### Inheritance rule

Reporting deadlines cascade by default:

Subsidiary Deadline
  → BU Deadline
      → Project Deadline

A BU inherits the applicable subsidiary deadline unless an authorized override applies.

## 23. REPORT STATUS MODEL

Use a workflow status and a separate deadline status.

### Workflow status

- Draft.
- Submitted.
- Pending Review.
- Approved.
- Rejected.

After rejection, the responsible user must correct the report and resubmit it.

A resubmission creates a new version or submission revision and returns the record to the configured review workflow.

### Deadline status

- Not Started.
- Upcoming.
- Due Soon.
- Submitted On Time.
- Submitted Late.
- Overdue.
- Closed.

Overdue is not a mutually exclusive workflow status.

For example, a report can be Pending Review while the review deadline is overdue, or Rejected while the correction deadline has passed.

Store the applicable deadline type and calculate overdue state from the actual workflow stage.

### Automatic status behavior

When a user submits a report:

- Persist the submission.
- Record its version and timestamp.
- Update the dashboard.
- Add it to the appropriate monitoring view.
- Notify the Subsidiary Manager.
- Update applicable submission-completion metrics.

When the Subsidiary Manager approves:

- Persist the approval decision.
- Record reviewer, timestamp, and version.
- Update the report status.
- Update dashboard counts.
- Notify the responsible user and Subsidiary Admin.
- Make the approved data eligible for the next configured reporting stage.

When the Subsidiary Manager rejects:

- Require a rejection reason.
- Persist the decision and reviewed version.
- Notify the responsible BU/project user.
- Display the correction reason.
- Return the report to the correction workflow.
- Preserve the rejected version and its evidence.
- Update reporting metrics.

The Subsidiary Admin must not perform the approval or rejection transition.
