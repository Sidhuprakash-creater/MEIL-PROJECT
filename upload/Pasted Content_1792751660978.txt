## 2. FINAL ROLE DEFINITIONS

The organization hierarchy is:

Group Admin
  └── Subsidiary
      ├── Subsidiary Admin
      ├── Subsidiary Manager
      └── Business Units
          ├── BU Manager
          ├── BU Admin
          └── Projects / Sites
              └── Assigned Data Entry Users

The seven data-entry roles are:

1. Environment Data User.
2. Finance & Resource Contributor.
3. HR User.
4. EHS / Safety User.
5. Procurement User.
6. CSR / Community User.
7. Compliance User.

### Subsidiary Manager responsibilities

The Subsidiary Manager must:

- View the assigned subsidiary's reporting dashboard.
- Monitor BU and project reports.
- View submitted, pending, approved, rejected, and overdue reports.
- Review complete submitted report content.
- Verify supporting evidence.
- Approve satisfactory reports.
- Reject incorrect, incomplete, or inadequately supported reports.
- Provide a mandatory rejection reason.
- Return rejected reports to the responsible BU/project user for correction.
- Review corrected and resubmitted reports.
- Monitor reporting deadlines.
- Inspect reporting activity and previous decisions.
- Track reporting completeness and data-quality issues.
- View relevant subsidiary-level ESG analytics.

### Explicit restrictions

The Subsidiary Manager must NOT:

- Create Business Units.
- Add projects.
- Edit the organizational hierarchy by creating or moving BUs/projects.
- Manage users or roles by default.
- Override Group-level security policies.
- Change centrally mandated reporting rules.
- Create or finalize the consolidated Group BRSR report.
- Access another subsidiary without explicit authorization.
- Approve or reject reports that are outside their assigned review authority.

The Subsidiary Admin remains responsible for organizational administration, project creation, reporting timelines, and report monitoring.

The Subsidiary Manager is responsible for report verification and approval/rejection.

The Group Admin owns group-wide consolidation and the consolidated BRSR report.

## 11. APPROVE WORKFLOW

When the manager selects Approve:

1. Verify that the manager is authorized to review this report.
2. Confirm that the report is in an eligible state.
3. Confirm that the version being reviewed is still the current eligible version.
4. Check mandatory review requirements.
5. Show a confirmation dialog containing the report identity.
6. Allow the manager to confirm or cancel.
7. Persist the decision using the backend.
8. Record the reviewer, timestamp, report version, and decision.
9. Update the report workflow state.
10. Update dashboard and queue counts.
11. Notify the responsible user.
12. Notify the Subsidiary Admin.
13. Make the approved report eligible for the next configured reporting stage.
14. Refresh relevant reporting views.

Handle concurrent review decisions safely.

If the report changes after the manager opens it, require a refresh or renewed review rather than approving an outdated version.

An approved report must not be silently overwritten. Any permitted correction after approval must follow an auditable revision or reopening workflow.

## 12. REJECT WORKFLOW

Rejection requires a mandatory reason.

When the manager selects Reject:

1. Verify review permissions.
2. Verify the report's current state and version.
3. Open a rejection dialog.
4. Display the report identity.
5. Require a meaningful rejection reason.
6. Allow specific correction instructions.
7. Optionally identify the affected report fields or evidence items.
8. Confirm the decision.
9. Persist the rejection reason and decision.
10. Record reviewer identity, timestamp, and report version.
11. Update the workflow state.
12. Notify the responsible BU/project user.
13. Notify the Subsidiary Admin.
14. Return the report to the correction workflow.
15. Preserve the rejected version and its evidence.

The rejection dialog must validate the reason and prevent accidental empty submissions.

Never silently discard a report or overwrite its history.

## 19. REPORT STATUS MODEL

Use workflow state separately from deadline state.

### Workflow state

- Draft.
- Submitted.
- Pending Review.
- Approved.
- Rejected.

A corrected report is resubmitted as a new version/revision and returns to the configured review workflow.

### Deadline state

- Not Started.
- Upcoming.
- Due Soon.
- Submitted On Time.
- Submitted Late.
- Overdue.
- Closed.

Overdue is a calculated condition, not a mutually exclusive workflow status.

A report can be Pending Review and overdue for review, or Rejected and overdue for correction.

Store the deadline type and calculate the status from the applicable workflow stage.

### Dashboard counting rules

Define explicitly whether each metric counts:

- Unique report records.
- Unique reporting periods.
- Unique BUs.
- Unique projects.

Never combine these measures into a single ambiguous count.

The same backend query definitions must drive dashboard KPIs and filtered destination screens.
