## 1. YOUR ROLE

Act as a senior enterprise software architect, full-stack engineer, UI/UX designer, motion designer, database architect, security engineer, and ESG/BRSR reporting specialist.

Your task is to build a complete, production-oriented Group Admin Workspace for the MEIL ESG & BRSR Reporting Platform.

Do not build a static dashboard, a UI-only prototype, or a collection of disconnected pages. Build a cohesive application with working navigation, persistent data, role-aware permissions, functional forms, reporting workflows, interactive analytics, real validation, and connected modules.

## 2. NON-NEGOTIABLE ROLE DEFINITION

SUPER ADMIN = GROUP ADMIN.

These are two names for the SAME role in this project. Never create two separate roles, dashboards, account types, or authorization layers for them.

The Group Admin is the highest organizational-level administrator in this application's defined role hierarchy.

The Group Admin can manage the complete authorized organizational scope, including subsidiaries, business units, projects, users, submissions, approvals, ESG analytics, audit records, and consolidated BRSR reporting.

The Group Admin is responsible for creating, reviewing, coordinating sign-offs for, and finalizing the consolidated BRSR report according to configured permissions and reporting requirements.

### Existing role hierarchy

Group Admin
  └── Subsidiaries
      └── Subsidiary Manager
      └── Subsidiary Admin
          └── Business Units
              └── BU Manager
              └── BU Admin
                  └── Project / Site Users

### Seven Data Entry User roles

1. Environment Data User
2. Finance & Resource Contributor
3. HR User
4. EHS / Safety User
5. Procurement User
6. CSR / Community User
7. Compliance User

There are 11 defined role types in total: one Group Admin, two subsidiary roles, two BU roles, and seven data-entry roles.

These are role types, not fixed user counts. Support multiple users in each role and multiple projects, BUs, and subsidiaries.

Preserve the organization hierarchy:

GROUP → SUBSIDIARY → BUSINESS UNIT → PROJECT / SITE

The Group Admin must be able to inspect the entire organization through searchable tables, hierarchy views, detail pages, filters, and drill-down navigation.

Do not assume actual company counts, real users, reporting figures, or organizational records. Use existing backend data where available and clearly identified demo data when necessary.

## 3. CORE PRODUCT OBJECTIVE

Build a centralized ESG command center where the Group Admin can:

- Monitor all subsidiaries, BUs, projects, and users.
- Create, edit, invite, reassign, suspend, reactivate, and deactivate users.
- Manage role assignments and organization-scoped permissions.
- View all eligible submissions and their responsible users.
- Identify pending, overdue, rejected, returned, and approved reports.
- Inspect report values, supporting documents, evidence, and previous versions.
- Approve, reject, return, reopen, or request corrections where authorized.
- Assign tasks and reporting deadlines to individuals, role groups, BUs, subsidiaries, or eligible Group-wide audiences.
- Send notifications, reminders, and announcements.
- Monitor user activity and maintain traceable audit records.
- Validate and consolidate ESG data.
- Create a new BRSR report using a guided wizard.
- Review and edit the generated report draft.
- Route the report through configured reviews and required sign-offs.
- Finalize, version, and export the approved report.
- Analyze ESG performance and submission completion.
- Configure reporting periods, metric definitions, workflows, integrations, and system settings.

Every module must share consistent data, permissions, organization context, and reporting-period logic.

Use the supplied MEIL Group Admin workspace reference image as the primary visual reference.

### Visual identity

- Primary atmosphere: very light sky blue.
- Base surfaces: white and pale blue-white.

- Secondary accents: restrained purple, teal, green, and amber for meaningful statuses.

- Typography: Inter or the existing project font.
- Icons: consistent professional outline icons, preferably Lucide or the existing icon library.

Use these as starting values and integrate them with the existing theme system rather than duplicating design tokens.

### iOS Liquid Glass and glassmorphism

Apply a refined, enterprise-appropriate Liquid Glass appearance:

- Translucent white and pale-blue surfaces.
- Frosted backgrounds with restrained backdrop blur.
- Subtle inner highlights and thin translucent borders.
- Layered ambient shadows and soft blue illumination.
- Gentle reflective gradients on selected panels.
- Consistent rounded cards, dialogs, menus, and dropdowns.
- Clear foreground/background contrast.
- Solid fallback surfaces when backdrop filtering is unavailable.

Example CSS approach:

.glass-panel {
  background: rgba(255, 255, 255, 0.66);
  backdrop-filter: blur(24px) saturate(145%);
  -webkit-backdrop-filter: blur(24px) saturate(145%);
  border: 1px solid rgba(255, 255, 255, 0.82);
  border-radius: 24px;
  box-shadow:
    0 10px 30px rgba(55, 111, 157, 0.08),
    0 2px 8px rgba(55, 111, 157, 0.04),
    inset 0 1px 0 rgba(255, 255, 255, 0.85);
}

Do not apply glass effects to every element indiscriminately. Use visual hierarchy, solid high-contrast surfaces for dense data, and stronger glass treatments for navigation, overview panels, floating toolbars, and prominent cards.

Preserve readable text, accessible focus states, and usable tables.
