    22→## 2. FINAL ROLE DEFINITIONS — NON-NEGOTIABLE
    23→
    24→The platform has the following organizational hierarchy:
    25→
    26→GROUP
    27→  └── SUBSIDIARY
    28→      └── BUSINESS UNIT (BU)
    29→          └── PROJECT / SITE
    30→              └── Assigned Data Entry Users
    31→
    32→The role hierarchy is:
    33→
    34→1. Group Admin (also called Super Admin — the same role).
    35→2. Subsidiary Admin.
    36→3. Subsidiary Manager.
    37→4. BU Manager.
    38→5. BU Admin.
    39→6. Seven Data Entry User roles.
    40→
    41→The seven Data Entry User roles are:
    42→
    43→- Environment Data User.
    44→- Finance & Resource Contributor.
    45→- HR User.
    46→- EHS / Safety User.
    47→- Procurement User.
    48→- CSR / Community User.
    49→- Compliance User.
    50→
    51→### Subsidiary Admin — primary responsibility
    52→
    53→The Subsidiary Admin is responsible for:
    54→
    55→- Managing business units within the assigned subsidiary.
    56→- Creating projects under the correct business units.
    57→- Managing authorized organizational assignments.
    58→- Setting reporting timelines at subsidiary, BU, and project levels.
    59→- Using inherited deadlines by default.
    60→- Monitoring submitted, pending, approved, rejected, and overdue reports.
    61→- Opening and reading BU and project reports.
    62→- Inspecting supporting evidence without leaving the report workflow.
    63→- Monitoring user activity, reporting progress, missing submissions, and validation issues.
    64→- Preparing subsidiary-level ESG reporting packages.
    65→- Submitting eligible subsidiary reporting data to the Group Admin's reporting workflow.
    66→
    67→### Subsidiary Admin must NOT
    68→
    69→- Approve or reject BU reports.
    70→- Approve or reject project reports.
    71→- Override the Subsidiary Manager's review decisions.
    72→- Create another Group Admin or grant Group Admin permissions.
    73→- Access or modify another subsidiary without explicit authorization.
    74→- Independently create or finalize the consolidated Group BRSR report.
    75→- Override mandatory Group-level reporting policies without authorization.
    76→
    77→The Subsidiary Admin's role is organizational administration, timeline management, reporting operations, and monitoring.
    78→
    79→### Subsidiary Manager — separate role
    80→
    81→The Subsidiary Manager is a separate role at the same subsidiary level.
    82→
    83→The Subsidiary Manager is responsible for:
    84→
    85→- Reviewing submitted BU and project reports.
    86→- Inspecting the full report and its evidence.
    87→- Approving or rejecting reports.
    88→- Providing a mandatory rejection reason.
    89→- Sending rejected reports back to the responsible BU/project user for correction and resubmission.
    90→- Monitoring reporting progress and review queues.
    91→
    92→The Subsidiary Manager cannot create new BUs or projects.
    93→
    94→The Subsidiary Manager's approval decisions must appear in the Subsidiary Admin's report-monitoring views, but the Subsidiary Admin must not receive approval/rejection controls.
    95→
    96→### Group Admin ownership
    97→
    98→The Group Admin owns:
    99→
   100→- Group-wide reporting governance.
   101→- Consolidation across applicable subsidiaries.
   102→- Final BRSR disclosure mapping.
   103→- Creation and management of the consolidated Group BRSR report.
   104→- Required Group-level sign-offs and finalization.
   105→- Group-wide organizational and security policies.
   106→
   107→The Subsidiary Admin may prepare and submit subsidiary-level reporting packages, but must never replace the Group Admin as owner of the consolidated Group BRSR report.

  1205→## 23. REPORT STATUS MODEL
  1206→
  1207→Use a workflow status and a separate deadline status.
  1208→
  1209→### Workflow status
  1210→
  1211→- Draft.
  1212→- Submitted.
  1213→- Pending Review.
  1214→- Approved.
  1215→- Rejected.
  1216→
  1217→After rejection, the responsible user must correct the report and resubmit it.
  1218→
  1219→A resubmission creates a new version or submission revision and returns the record to the configured review workflow.
  1220→
  1221→### Deadline status
  1222→
  1223→- Not Started.
  1224→- Upcoming.
  1225→- Due Soon.
  1226→- Submitted On Time.
  1227→- Submitted Late.
  1228→- Overdue.
  1229→- Closed.
  1230→
  1231→Overdue is not a mutually exclusive workflow status.
  1232→
  1233→For example, a report can be Pending Review while the review deadline is overdue, or Rejected while the correction deadline has passed.
  1234→
  1235→Store the applicable deadline type and calculate overdue state from the actual workflow stage.
  1236→
  1237→### Automatic status behavior
  1238→
  1239→When a user submits a report:
  1240→
  1241→- Persist the submission.
  1242→- Record its version and timestamp.
  1243→- Update the dashboard.
  1244→- Add it to the appropriate monitoring view.
  1245→- Notify the Subsidiary Manager.
  1246→- Update applicable submission-completion metrics.
  1247→
  1248→When the Subsidiary Manager approves:
  1249→
  1250→- Persist the approval decision.
  1251→- Record reviewer, timestamp, and version.
  1252→- Update the report status.
  1253→- Update dashboard counts.
  1254→- Notify the responsible user and Subsidiary Admin.
  1255→- Make the approved data eligible for the next configured reporting stage.
  1256→
  1257→When the Subsidiary Manager rejects:
  1258→
  1259→- Require a rejection reason.
  1260→- Persist the decision and reviewed version.
  1261→- Notify the responsible BU/project user.
  1262→- Display the correction reason.
  1263→- Return the report to the correction workflow.
  1264→- Preserve the rejected version and its evidence.
  1265→- Update reporting metrics.
  1266→
  1267→The Subsidiary Admin must not perform the approval or rejection transition.
  1268→
