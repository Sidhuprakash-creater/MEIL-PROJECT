    12→# 1. Non-Negotiable Design Direction
    13→
    14→Create a distinctive, premium enterprise interface called:
    15→
    16→**“Liquid Intelligence — Business Operations & ESG Review”**
    17→
    18→The visual language must be noticeably different from the existing Group Admin and Subsidiary workspaces while still feeling like part of the same MEIL platform.
    19→
    20→Do not copy their screen layouts, dashboard compositions, card arrangements, navigation patterns, or component styling. Create a fresh visual identity for these two workspaces without changing or breaking other workspaces.
    21→
    22→### Core design characteristics
    23→
    24→- Premium sky-blue atmosphere with liquid-purple accents.
    25→- iOS-inspired Liquid Glass and refined glassmorphism.
    26→- Translucent, frosted panels with layered depth.
    27→- Soft directional shadows and subtle ambient lighting.
    28→- Floating analytics cards with carefully controlled elevation.
    29→- Smooth animated charts, progress bars, counters, and status transitions.
    30→- Refined typography and generous spacing.
    31→- High-quality Lucide icons instead of emojis.
    32→- Clear information hierarchy suitable for enterprise ESG reporting.
    33→- A clean, bright interface with restrained color and professional contrast.
    34→- Desktop-first productivity, with excellent tablet and mobile responsiveness.
    35→
    36→The application should feel sophisticated, precise, responsive, and alive—not like a generic admin template or an overly futuristic sci-fi dashboard.

    59→### Liquid Glass surface specification
    60→
    61→Every major card and panel should use a carefully tuned combination of:
    62→
    63→- Semi-transparent white or pale-blue background.
    64→- `backdrop-filter: blur(16px–24px)` where supported.
    65→- Fine, low-contrast borders.
    66→- Soft outer shadows with a subtle blue or purple tint.
    67→- Optional subtle inner highlight.
    68→- Rounded corners generally between 16px and 24px.
    69→- Consistent internal padding and alignment.
    70→
    71→Example shadow direction:
    72→
    73→`0 12px 34px rgba(65, 110, 190, 0.09)`
    74→
    75→Use stronger shadows on floating action surfaces and elevated cards, but do not make every component equally elevated. Establish a consistent depth hierarchy.
    76→
    77→Maintain readability and sufficient contrast. Provide solid-background fallbacks where backdrop filtering is unavailable.
    78→
    79→### Button styling
    80→
    81→**Primary buttons:** liquid-purple gradient, white text, subtle purple shadow, 12–14px radius, clear icon and label.
    82→
    83→**Secondary buttons:** translucent white glass, sky-blue border, graphite or blue text.
    84→
    85→**Positive actions:** restrained green accent, particularly for valid submissions and completed actions.
    86→
    87→**Destructive actions:** muted red styling with a confirmation step.
    88→
    89→**Icon buttons:** compact glass surfaces with tooltips, clear hover/focus states, and accessible labels.
    90→
    91→Every interactive control must have default, hover, focus, pressed, disabled, loading, and success/error states where applicable.
    92→
    93→Do not use excessive gradients, neon glows, huge rounded pills everywhere, or decorative effects that reduce usability.

   912→### Review workflow
   913→
   914→Implement the following process:
   915→
   916→1. A Project User or Data Entry User submits a report.
   917→2. The report enters the configured BU-level review workflow.
   918→3. The BU Manager opens the submission.
   919→4. The manager checks completeness, data quality, calculations, and supporting evidence.
   920→5. The manager records comments and identifies issues.
   921→6. If correction is required, the manager returns the report with a mandatory reason and actionable comments.
   922→7. The responsible user corrects the report and resubmits a new version.
   923→8. The manager reviews the new version and can compare it against the previous version.
   924→9. When the report satisfies the configured requirements, the manager approves it.
   925→10. The approved report advances to the next configured stage, such as Subsidiary Manager review, if applicable.
   926→11. Eligible approved data becomes available to the authorized upward reporting and Group BRSR consolidation process.
   927→
   928→Both project reports and data-entry reports must follow the configured BU-level review workflow. No unauthorized bypass is allowed.
   929→

   931→
   932→**Approve**
   933→
   934→- Show a confirmation dialog.
   935→- Summarize the report and version being approved.
   936→- Allow an optional decision comment.
   937→- Persist the decision and audit event.
   938→- Update workflow status.
   939→- Advance to the next configured stage.
   940→
   941→**Return for Correction**
   942→
   943→- Require a reason.
   944→- Require actionable correction details according to the configured policy.
   945→- Allow comments associated with specific fields where supported.
   946→- Confirm the action before submission.
   947→- Persist the decision and revision relationship.
   948→- Notify the responsible user.
   949→- Return the report to the authorized correction stage.
   950→
   951→**Reject**
   952→
   953→- Display only if permitted by the configured workflow.
   954→- Require a mandatory rejection reason.
   955→- Confirm the action.
   956→- Persist the decision, actor, timestamp, version, and reason.
   957→- Trigger the appropriate workflow and notification events.
   958→
   959→All review actions must be implemented in the backend, not merely displayed or hidden in the frontend.

   965→Keep workflow state separate from deadline state.
   966→

   968→
   969→- Draft.
   970→- Submitted.
   971→- Pending Review.
   972→- Under Review.
   973→- Returned for Correction.
   974→- Approved.
   975→- Rejected.
   976→
   977→Use only the states supported by the existing workflow model and map existing equivalent states instead of creating duplicate status systems.
   978→
   979→### Deadline states
   980→
   981→- Not Started.
   982→- Upcoming.
   983→- Due Soon.
   984→- Submitted On Time.
   985→- Submitted Late.
   986→- Overdue.
   987→- Closed.
   988→
   989→Overdue is a computed deadline condition, not an exclusive workflow state.
   990→
   991→Examples:
   992→

   994→- A report can be Approved after its submission deadline.
   995→- A report can be Returned for Correction while the correction deadline is approaching.
   996→
   997→Track separate timestamps for submission, review start, decision, resubmission, and closure where applicable.
   998→
   999→Define the deadline calculation and time-zone rules centrally so every screen produces consistent results.

  1001→### Dashboard and table consistency
  1002→

  1004→
  1005→Define whether metrics count report records, projects, reporting periods, or unique reporting entities. Label them accordingly.
  1006→
  1007→Prevent duplicate counting when one project has multiple reports or reporting periods.
