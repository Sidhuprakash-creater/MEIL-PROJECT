    16→## 2. FINAL ROLE DEFINITIONS
    17→
    18→The organization hierarchy is:
    19→
    20→Group Admin
    21→  └── Subsidiary
    22→      ├── Subsidiary Admin
    23→      ├── Subsidiary Manager
    24→      └── Business Units
    25→          ├── BU Manager
    26→          ├── BU Admin
    27→          └── Projects / Sites
    28→              └── Assigned Data Entry Users
    29→
    30→The seven data-entry roles are:
    31→
    32→1. Environment Data User.
    33→2. Finance & Resource Contributor.
    34→3. HR User.
    35→4. EHS / Safety User.
    36→5. Procurement User.
    37→6. CSR / Community User.
    38→7. Compliance User.
    39→
    40→### Subsidiary Manager responsibilities
    41→
    42→The Subsidiary Manager must:
    43→
    44→- View the assigned subsidiary's reporting dashboard.
    45→- Monitor BU and project reports.
    46→- View submitted, pending, approved, rejected, and overdue reports.
    47→- Review complete submitted report content.
    48→- Verify supporting evidence.
    49→- Approve satisfactory reports.
    50→- Reject incorrect, incomplete, or inadequately supported reports.
    51→- Provide a mandatory rejection reason.
    52→- Return rejected reports to the responsible BU/project user for correction.
    53→- Review corrected and resubmitted reports.
    54→- Monitor reporting deadlines.
    55→- Inspect reporting activity and previous decisions.
    56→- Track reporting completeness and data-quality issues.
    57→- View relevant subsidiary-level ESG analytics.
    58→
    59→### Explicit restrictions
    60→
    61→The Subsidiary Manager must NOT:
    62→
    63→- Create Business Units.
    64→- Add projects.
    65→- Edit the organizational hierarchy by creating or moving BUs/projects.
    66→- Manage users or roles by default.
    67→- Override Group-level security policies.
    68→- Change centrally mandated reporting rules.
    69→- Create or finalize the consolidated Group BRSR report.
    70→- Access another subsidiary without explicit authorization.
    71→- Approve or reject reports that are outside their assigned review authority.
    72→
    73→The Subsidiary Admin remains responsible for organizational administration, project creation, reporting timelines, and report monitoring.
    74→
    75→The Subsidiary Manager is responsible for report verification and approval/rejection.
    76→
    77→The Group Admin owns group-wide consolidation and the consolidated BRSR report.

   499→## 11. APPROVE WORKFLOW
   500→
   501→When the manager selects Approve:
   502→
   503→1. Verify that the manager is authorized to review this report.
   504→2. Confirm that the report is in an eligible state.
   505→3. Confirm that the version being reviewed is still the current eligible version.
   506→4. Check mandatory review requirements.
   507→5. Show a confirmation dialog containing the report identity.
   508→6. Allow the manager to confirm or cancel.
   509→7. Persist the decision using the backend.
   510→8. Record the reviewer, timestamp, report version, and decision.
   511→9. Update the report workflow state.
   512→10. Update dashboard and queue counts.
   513→11. Notify the responsible user.
   514→12. Notify the Subsidiary Admin.
   515→13. Make the approved report eligible for the next configured reporting stage.
   516→14. Refresh relevant reporting views.
   517→
   518→Handle concurrent review decisions safely.
   519→
   520→If the report changes after the manager opens it, require a refresh or renewed review rather than approving an outdated version.
   521→
   522→An approved report must not be silently overwritten. Any permitted correction after approval must follow an auditable revision or reopening workflow.
   523→
   524→## 12. REJECT WORKFLOW
   525→
   526→Rejection requires a mandatory reason.
   527→
   528→When the manager selects Reject:
   529→
   530→1. Verify review permissions.
   531→2. Verify the report's current state and version.
   532→3. Open a rejection dialog.
   533→4. Display the report identity.
   534→5. Require a meaningful rejection reason.
   535→6. Allow specific correction instructions.
   536→7. Optionally identify the affected report fields or evidence items.
   537→8. Confirm the decision.
   538→9. Persist the rejection reason and decision.
   539→10. Record reviewer identity, timestamp, and report version.
   540→11. Update the workflow state.
   541→12. Notify the responsible BU/project user.
   542→13. Notify the Subsidiary Admin.
   543→14. Return the report to the correction workflow.
   544→15. Preserve the rejected version and its evidence.
   545→
   546→The rejection dialog must validate the reason and prevent accidental empty submissions.
   547→
   548→Never silently discard a report or overwrite its history.

   786→## 19. REPORT STATUS MODEL
   787→
   788→Use workflow state separately from deadline state.
   789→
   790→### Workflow state
   791→
   792→- Draft.
   793→- Submitted.
   794→- Pending Review.
   795→- Approved.
   796→- Rejected.
   797→
   798→A corrected report is resubmitted as a new version/revision and returns to the configured review workflow.
   799→
   800→### Deadline state
   801→
   802→- Not Started.
   803→- Upcoming.
   804→- Due Soon.
   805→- Submitted On Time.
   806→- Submitted Late.
   807→- Overdue.
   808→- Closed.
   809→
   810→Overdue is a calculated condition, not a mutually exclusive workflow status.
   811→
   812→A report can be Pending Review and overdue for review, or Rejected and overdue for correction.
   813→
   814→Store the deadline type and calculate the status from the applicable workflow stage.
   815→
   816→### Dashboard counting rules
   817→
   818→Define explicitly whether each metric counts:
   819→
   820→- Unique report records.
   821→- Unique reporting periods.
   822→- Unique BUs.
   823→- Unique projects.
   824→
   825→Never combine these measures into a single ambiguous count.
   826→
   827→The same backend query definitions must drive dashboard KPIs and filtered destination screens.
