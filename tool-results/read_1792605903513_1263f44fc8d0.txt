    18→## 2. NON-NEGOTIABLE ROLE DEFINITION
    19→
    20→SUPER ADMIN = GROUP ADMIN.
    21→
    22→These are two names for the SAME role in this project. Never create two separate roles, dashboards, account types, or authorization layers for them.
    23→
    24→The Group Admin is the highest organizational-level administrator in this application's defined role hierarchy.
    25→
    26→The Group Admin can manage the complete authorized organizational scope, including subsidiaries, business units, projects, users, submissions, approvals, ESG analytics, audit records, and consolidated BRSR reporting.
    27→
    28→The Group Admin is responsible for creating, reviewing, coordinating sign-offs for, and finalizing the consolidated BRSR report according to configured permissions and reporting requirements.
    29→
    30→### Existing role hierarchy
    31→
    32→Group Admin
    33→  └── Subsidiaries
    34→      └── Subsidiary Manager
    35→      └── Subsidiary Admin
    36→          └── Business Units
    37→              └── BU Manager
    38→              └── BU Admin
    39→                  └── Project / Site Users
    40→
    41→### Seven Data Entry User roles
    42→
    43→1. Environment Data User
    44→2. Finance & Resource Contributor
    45→3. HR User
    46→4. EHS / Safety User
    47→5. Procurement User
    48→6. CSR / Community User
    49→7. Compliance User
    50→
    51→There are 11 defined role types in total: one Group Admin, two subsidiary roles, two BU roles, and seven data-entry roles.
    52→
    53→These are role types, not fixed user counts. Support multiple users in each role and multiple projects, BUs, and subsidiaries.
    54→
    55→Preserve the organization hierarchy:
    56→
    57→GROUP → SUBSIDIARY → BUSINESS UNIT → PROJECT / SITE
    58→
    59→The Group Admin must be able to inspect the entire organization through searchable tables, hierarchy views, detail pages, filters, and drill-down navigation.
    60→
    61→Do not assume actual company counts, real users, reporting figures, or organizational records. Use existing backend data where available and clearly identified demo data when necessary.
